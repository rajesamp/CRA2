# C5 implementation plan for review

On November 23, 2026 the owner accepted the [C5 spec](spec.md) at `7319310` and selected Python 3.13 for future checks. The owner will review this plan before implementation. C5 will let a reviewer answer “Which code and evidence produced this review?” and let the operator verify that answer against the image receiving traffic.

## Work in order

1. **Define the release record and its checks.** Add `scripts/release_record.py` and `week2/tests/test_release_record.py`. Start with failing tests for a wrong source, changed dataset and a green PR with no serving observation. Define schema version 1 with a bundle ID, full source commit, component and entrypoint, a dated manifest of input hashes, and separate entries for PR status, local tests, hosted tests, build, traffic and owner acceptance. Each entry carries the subject it describes, a UTC time, scope, result and durable evidence reference. Represent missing evidence explicitly. An owner decision requires a dated reference and the exact release and behavior accepted. Store a redacted operator summary under `docs/evidence/releases/`. Accept only the documented fields. Exclude account names, private URLs, bucket names, prompts and raw identity or session records.

2. **Bind the build to the evidence it actually uses.** Generate the identity from a clean checkout of the full source commit. Hash the shipped bytes of `data/checkout_system.json`, `data/incidents.json`, `data/sample_incidents.json`, `week1/corpus/manifest.json` and its referenced documents. Compare the index's corpus and encoder fingerprints with the values produced by `week1/retrieval.py` and the verified model from `week1/setup_index.py`. Derive a stable dataset ID from a canonical sorted manifest using relative paths. Capture the digest of the public C3 development packet, grading key and controls, the retrieval cases and the evaluator revision in the operator record. Use the existing C3 digest functions where those reports already bind the inputs. Report unknown for missing historical inputs. Generate a separate, minimal `week2/_release.json` containing only the bundle ID, source revision and dataset ID. Update `Containerfile`, `.dockerignore` and the image workflow so the Podman build recomputes or verifies the packaged input hashes. A source or dataset mismatch must fail the release check. A local launch without build metadata remains usable.

3. **Display the label after sign-in.** Read the packaged fields through a small loader in `week2/release_info.py`. Show one line beneath the CRA title in `week2/app.py`, for example “Release V1 · Source abc1234 · Dataset 78b26fa1” for a synthetic fixture. Missing, malformed or unsupported metadata produces “Local build · Release unverified”. Use plain, length-limited fields and load without network, Git, registry or cloud calls. Exercise the normal `week2.cloud_app` mount with its signed synthetic owner. The separate `week2.landing` process keeps its static public version. Inspect the public responses for seeded private data and exercise the existing sign-in redirect contract.

4. **Verify the published image and serving observations.** Extend the operator verifier and the procedure in `docs/cloud-run-plan.md`. Use `scripts/check_container.py` and `scripts/scan_container.py` to check the local image/config identity. Resolve the registry manifest and its referenced config for the target platform, then require the signature and provenance to identify that exact final manifest and the build's source. Keep these observations in the external operator record, outside the image. Changing an embedded file after signing would change the digest. Accept dated, read-only traffic observations for both components and resolve every positive-traffic revision to its manifest. Check percentages independently per component and preserve split traffic. Record unknown on missing observations and retain the timestamp on earlier observations. Compare the protected browser label only to the revision observed serving the request. If the revision cannot be identified in a split, record that check as unresolved. A failed comparison prevents a verified promotion claim.

5. **Keep verification usable from a fresh checkout.** Extend `.github/workflows/week2-4.yml` and `.github/workflows/container-security.yml` with release verification on Python 3.13. Record the PR head, the checked-out commit and the CI run URL separately. Use the existing build, scan, C1–C4 and offline evaluator jobs. Record redacted result counts, input digests and stable evidence references in version control before the hosted artifacts expire. Add a reproducible signed-owner smoke procedure to `docs/cloud-run-plan.md`, using the locked Python 3.13 environment, verified encoder, local storage fixture and network-disabled Podman checks. Reuse the signed browser setup from `evaluation/probe_audit_browser.py` through a targeted probe. Each result identifies whether it was observed locally, in hosted CI or on a serving revision.

## Acceptance checks

| Exercise | Required observation |
|---|---|
| Read records for serving V1, a green unserved PR and locally tested C4 | Software, build, serving and acceptance each show their own evidence. V1 owner acceptance stays pending unless the owner identifies that release. |
| Alter the source, catalog bytes, an incident, a retrieval document, the rubric, CI subject, or an image binding | Each change identifies its failed check. A local config digest cannot satisfy a registry manifest check. |
| Supply zero traffic, a 70/30 split, an unavailable observation and a label mismatch | Only positive shares appear as serving, both split revisions are listed, and unknowns or mismatches cannot pass verification. |
| Render valid, missing and malformed metadata through the signed owner mount | The owner sees the expected label or local fallback. Loading the label makes zero network requests. The anonymous intro and redirect responses disclose zero seeded private values. |
| Repeat from a clean checkout after removing the short-lived CI artifact | The committed summary resolves to the tested source, input versions, bounded checks and original run URL. Reproducing a local test does not refresh the date of the historical deployment observation. |
| Present an earlier demo sign-off, a C3 public-control result, or a C2 local capacity run | The corresponding owner acceptance, independent grading or cloud capacity assessment stays pending for the new candidate. |

The critical release risk is attributing a valid scan, signature, CI result or browser label to the wrong image. Test each binding independently, including a mixed-version rollout. C5 implementation ends with local and hosted candidate evidence and a procedure for later owner verification. A live deployment, merge, invitations and independent labeling each require separate authorization.

The owner approved local implementation on November 23. The implementation keeps signed image evidence verification in `scripts/release_publication.py` beside the operator CLI, and reuses the existing browser driver from `evaluation/probe_release_browser.py`. The clean build context comes from a Git archive of the named commit. This binds packaged source bytes to the commit before Podman runs.
