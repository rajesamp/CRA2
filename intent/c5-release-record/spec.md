## Required behavior

1. **Give each build a reproducible identity.** Keep a machine-readable release record with a schema version, full source commit, bundle identifier, component names and entrypoints, dated source manifests, and evaluator, case packet and rubric revisions when applicable. Fingerprint the actual catalog, incident sources and retrieval manifest used by the build. Bind scan, signature and provenance evidence to the final registry digest after the image exists. Embed the source and evidence versions in the image and keep the final manifest digest in the separate release record. A deployment observation records its UTC time, traffic percentages and the resolved digest of every serving revision.
2. **Show a concise label in the protected app.** Show the visitor a release identifier, short source revision and dataset version or evidence date. A local build displays a local or unverified label when metadata is missing. The label works from packaged metadata with external access disabled. The public intro may identify its own version. It must not expose protected audit records, private service URLs, registry paths, account identifiers or operational details.
3. **Keep each kind of evidence attributable.** Track code/PR status, local verification, hosted verification, build evidence, serving state and owner acceptance independently. A green PR cannot assert deployment. A ready revision with zero traffic cannot assert serving. During a split rollout, show each serving component and its traffic share. Capture success, failure or unknown for each check with its scope, date, evidence reference and exact subject. Distinguish the PR head from a synthetic merge commit when CI uses one.
4. **Keep the record usable after the runner disappears.** Use repository-relative paths at immutable commits, stable CI run links and redacted content hashes for durable evidence. Record a bounded summary in version control when CI artifacts expire. Document how to repeat the local launch and verification with locked Python 3.13 dependencies, the verified encoder, synthetic storage and a signed synthetic owner. A temporary worktree, localhost URL or raw browser/session trace cannot be the sole evidence.
5. **Preserve explicit decisions and holds.** Record which release and behavior the owner accepted, with a dated reference. An absent decision stays pending. Do not backfill acceptance for older slices or infer it from a merged change or a browser smoke test. Keep invitations and independent labeling on hold. The C3 public controls, retrieval metrics and C2 local rehearsal cannot establish independent answer quality or 1,000-user cloud capacity.
6. **Verify a release before promotion.** A candidate shows the review dependencies and remaining release checks. The release procedure checks candidate digests, scan controls, signature and provenance before promotion. After an authorized rollout, verify owner-only access and match the displayed label to the revision actually receiving traffic. A mismatch blocks the claimed verification and leaves the observed state visible. This spec covers the record, label and verification procedure. Publishing, merging, new permissions and deployment require their own applicable authorization.

## Acceptance evidence

| Exercise | Observable passing result |
|---|---|
| Compare live V1, a green draft, and a locally verified candidate | The record reproduces the distinctions in the starting inventory. C4 cannot become live from its tests. A draft may legitimately be serving. |
| Supply mismatched source, manifest, config digest, dataset bytes, eval packet or CI subject | Each mismatch names the failed binding and prevents a verified release claim. Unavailable inputs remain unknown. A config digest cannot stand in for a registry manifest digest. |
| Give the verifier a zero-traffic ready revision, a split rollout and an unavailable observation | Only positive traffic counts as serving. A split lists both revisions and shares. An earlier observation retains its original timestamp. |
| Launch the signed owner fixture and the public intro, then remove or corrupt the label metadata | The owner sees the expected label or an explicit fallback. The public response contains zero private canaries. Loading the label causes zero network requests. |
| Reproduce the record from a clean checkout after an artifact expires | The committed, redacted summary still identifies the source, checks and evidence versions. The instructions distinguish rerunnable checks from historical observations and current owner decisions. |
| Try to reuse earlier owner acceptance or a synthetic result for a different release | The new acceptance remains pending. Access and labeling holds stay in force. |

**Owner review.** The design decision is whether the protected app should display the short source revision and dataset version, with detailed release and verification history in the operator record. After acceptance, the implementation plan can name the schema, build inputs, UI location and CI tests. C6 covers the broader product-copy correction.
