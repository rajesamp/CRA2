# C4 · Can the owner tell whether a preference was saved and which recovery checks ran?

**Implementation authorized · November 23, 2026.** C4 covers two paths in the protected app: a chat request that changes a durable preference, and a submission to the Incidents & rollback form. The owner should be able to reconstruct either operation after a restart using metadata alone. C3 commit `d7cba42` is the baseline. Its Python 3.13 CI passed and its seven public browser cases have recorded observations. [Accepted intent](../sdlc-review-2026-11-22/acceptance.md) · [C4 finding](../sdlc-review-2026-11-22/findings.md#c4--important-audit-completioncorrelation-is-incomplete) · [C3 CI](https://github.com/rajesamp/CRA2/actions/runs/45125461505/job/137528661190) · [Browser baseline](../c3-answer-quality/public-signed-browser.json)

## What the app records today

- Chat creates a `request_id`. The cloud preference adapter appends `memory_write_requested`, then writes the preference with a generation precondition. The audit entry has no chat request ID or corresponding result. If a later telemetry write fails, chat can return a generic availability error after the preference has already changed. [Chat workflow](https://github.com/rajesamp/CRA2/blob/d7cba426ea2b86ff796e825458605d77828459e4/week2/workflow.py) · [Cloud preference and audit adapters](https://github.com/rajesamp/CRA2/blob/d7cba426ea2b86ff796e825458605d77828459e4/week2/cloud_storage.py)
- The recovery form returns its admission decision and NeMo events to the current Gradio session. Its callback does not write a correlated recovery record to the compact telemetry store. Queue completion and a rendered report alone cannot establish which rails executed. [Recovery callback](https://github.com/rajesamp/CRA2/blob/d7cba426ea2b86ff796e825458605d77828459e4/week2/app.py) · [Guarded analysis](https://github.com/rajesamp/CRA2/blob/d7cba426ea2b86ff796e825458605d77828459e4/week2/incident_rollback.py) · [Session activity](https://github.com/rajesamp/CRA2/blob/d7cba426ea2b86ff796e825458605d77828459e4/week2/guardrail_activity.py) · [Telemetry projection](https://github.com/rajesamp/CRA2/blob/d7cba426ea2b86ff796e825458605d77828459e4/week4/telemetry.py)

## Preference writes

**R1 · Correlate one logical change.** Allocate an opaque, server-owned review ID at the trusted entry point and carry it through the workflow and telemetry. Link the requested and final audit events by a stable mutation ID tied to that review, the verified principal scope and the intended change. Duplicate delivery or a storage retry of that same change must produce at most one mutation and one logical terminal outcome. A separate owner edit gets a fresh ID. Reject reuse for a different scope, service or payload. Knowing an ID grants no access.

The private mutation audit records the schema version, event key, review and mutation IDs, UTC timestamp, event kind, allowlisted service, and bounded outcome or reason. A committed result includes a reference to evidence identifying the exact write. Give each logical event a stable key so a lost acknowledgement can be reconciled without creating a second outcome.

**R2 · Report the state write and the audit confirmation separately.** The owner authorized the following contract.

| What the application can establish | What the owner sees | What the operator can reconstruct |
|---|---|---|
| A fresh request cannot confirm its required pre-write audit entry or retention policy | “Preference was not changed.” Stop before submitting the state write. | This attempt issued no mutation. A lost audit acknowledgement may still leave a request entry. |
| State commit and terminal audit append are both confirmed | “Preference saved.” | The requested and committed events identify the same mutation and its durable commit evidence. |
| Storage definitively rejected the mutation, including exhausted generation conflicts where every attempted write was rejected | “Preference was not saved.” | Record a failed result with a bounded reason. If its append fails, retain the known state outcome for reconciliation. |
| State commit is confirmed, but the terminal audit append or later telemetry write fails | “Preference saved. Confirmation record incomplete.” | Preserve the commit evidence and identify which record is missing. Retry only the missing record. |
| Storage might have accepted the write, or a restart interrupts confirmation | “Save status unconfirmed.” | Mark the operation unresolved. Reconcile using durable evidence before permitting a repeat mutation. |

**R3 · Reconstruct after failure.** A request entry alone proves only that a write was requested. A matching current preference value, a timestamp, or a create conflict on an audit object is insufficient proof of that mutation. Preserve enough evidence to distinguish two successive edits, including two that set the same value. After restart, an authorized operator must be able to resolve recoverable gaps even if a later edit changed the preference. Keep unresolved cases explicit while proof is unavailable. Reconciliation must preserve newer values and create-only audit history. The implementation plan will specify the persistence mechanism, bounded retry window and reconciliation procedure after this contract is approved.

## Recovery reviews

**R4 · Record what executed.** Give each accepted recovery submission a review ID and emit one logical terminal telemetry record tied to its guarded callback. Include a schema version, operation, ID, timestamp, duration, final status and one bounded stage entry for admission, input, context and output. Each entry carries the engine, stage, outcome, reason code and execution flag from the actual decision or rail receipt. Allow, block, unavailable, not reached and not required must remain distinguishable. A missing or malformed receipt cannot count as a pass. A capacity refusal before the callback belongs to queue accounting and contributes zero executed checks. [Existing stage vocabulary](https://github.com/rajesamp/CRA2/blob/d7cba426ea2b86ff796e825458605d77828459e4/week2/guardrail_activity.py) · [Queue boundary](https://github.com/rajesamp/CRA2/blob/d7cba426ea2b86ff796e825458605d77828459e4/week2/capacity.py)

**R5 · Preserve the user's outcome.** A blocked stage withholds the report and the session panel shows where processing stopped. If required telemetry cannot be confirmed for an otherwise successful recovery review, withhold the report and show “The review record could not be confirmed. No recovery conclusion is available.” If a security block already occurred, keep that block visible. Record the missing telemetry as a gap in verification. Recovery remains advisory.

## Storage, privacy and compatibility

Use the existing private, create-only audit prefix for mutation events and the existing telemetry prefix for recovery records. Preserve the permanent 30-day audit lock, seven-day telemetry lifecycle and runtime IAM limits. Audit reads belong to the authorized operator. After telemetry expires, the retained audit must still answer the preference-write question within its own retention window. Lifecycle expiry is per object and deletion is asynchronous. [Storage contract and permissions](https://github.com/rajesamp/CRA2/blob/d7cba426ea2b86ff796e825458605d77828459e4/docs/cloud-durable-storage.md)

Allowlist versioned metadata fields and bounded values. Keep question text, preference values and notes, recovery form text, reports, credentials, emails, raw IAP subjects and browser session or delivery handles out of C4 audit, telemetry, diagnostics and CI evidence. An opaque scope reference needed for a private write audit stays there. The visitor's guardrail panel reads only its own session. Existing v1 preference records must remain readable and writable. Preserve historical request-only audit events as “completion unknown” and retain prior telemetry readers' ability to handle chat records. [Current storage reader](https://github.com/rajesamp/CRA2/blob/d7cba426ea2b86ff796e825458605d77828459e4/week2/cloud_storage.py) · [Access and privacy constraints](../sdlc-review-2026-11-22/intent.md#constraints)

Use the signed local owner fixture, the restartable object-store fixture and Python 3.13. Carry the C1–C3 and Week 2–4 checks forward. Use only synthetic accounts and inputs. Restart and redeliver each case. | Compare the durable state and operator reconstruction with the browser message. Repeat in isolated synthetic principal scopes. | One effect per logical mutation, preserved concurrent updates, correct correlation after restart and zero unauthorized cross-scope reads or writes. |

| Read legacy records, inject synthetic privacy canaries, and cross the seven- and 30-day lifecycle boundaries in the fixture. | Legacy data remains usable. New records and exported evidence contain zero canaries. Audit remains sufficient after telemetry expiry. Early audit overwrite and deletion remain denied. |

**Baseline check.** Six existing offline tests passed on Python 3.13.15 for process restart, concurrent preference updates, retention, pre-write audit failure, recovery NeMo execution and unavailable-stage display. The table above defines the additional proof required for C4.

Scope is application audit and telemetry. Cloud Run stays owner-only, invitations and independent labeling remain on hold, and the release record belongs to C5.
