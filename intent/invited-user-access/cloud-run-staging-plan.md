## 1. Verify the owner identity binding

**Owner enrollment.** Privately confirm the full Google account intended for this staging pilot. The current production owner stays in place. A local-part hint, repository author address, OAuth contact address or fixture identity cannot establish ownership. Initially expose only an identity check to the single confirmed IAP accessor. Give this mode no owner actions. Use a separate, deliberate enrollment step to pin the verified owner account ID in restricted staging configuration, then repeat the sign-in. Never automatically appoint the first visitor.

| Proof | Validation at the staging service |
|---|---|
| IAP authorized this request | Accept exactly one signed `x-goog-iap-jwt-assertion`. Validate its ES256 signature using IAP’s trusted public keys, issuer `https://cloud.google.com/iap`, issuance and expiry, and exact audience `/projects/PROJECT_NUMBER/locations/us-west1/services/cra2-invitations-staging`. Require the Google-user identity namespace. Ignore unsigned identity headers. [Signed IAP headers](https://docs.cloud.google.com/iap/docs/signed-headers-howto) |
| Google authenticated the browser user for this app | Use a staging-specific web OAuth client and exact HTTPS callback. Request only `openid email`. Use authorization code, PKCE S256, one-use state and nonce. Verify Google’s signature with its own trusted keys, a documented Google issuer, the staging app client ID as audience, authorized party where applicable, expiry, nonce and verified email. The IAP OAuth client and the app client have separate purposes and credentials. [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect) |
| The two verified identities are the enrolled owner | For the Google-account path, require the entire verified IAP subject to equal `accounts.google.com:` followed by the exact OIDC `sub`. Treat the ID as an opaque string. Compare the resulting account with the enrolled owner ID. With the existing IAP key contract, compute the expected IAP key from that exact namespaced subject and the IAP issuer. Reject unexpected formats, other providers and ambiguous claims. Email agreement is a secondary enrollment check. [Google token types and subject examples](https://docs.cloud.google.com/docs/authentication/token-types) |
| The binding belongs to this session | Bind the initial validated IAP identity, state, nonce and verifier to one short-lived server-side transaction. Require the same current IAP identity on callback. Consume the transaction atomically and rotate the session ID. On every protected request revalidate IAP and match it to the bound session and pinned owner. Changed identity, replay, expiry, missing configuration and unavailable verification keys close access. |

**Build and test locally first.** Add a separate staging auth adapter and binding tests under `invitations/`. Freeze the five probe cases above as regressions. Add callback replay, account switch between start and callback, same email/different owner pin, missing/expired assertions, key rotation/outage and fixture-credential rejection. Run the invitation and Week 2–4 Python 3.13 workflows. Keep the production verifier’s existing principal format and behavior intact.

**First live acceptance.** After approval to create staging, the owner opens the staging URL in a fresh browser, completes IAP and application Google sign-in, enrolls the verified ID through private configuration, and signs in again in a second fresh session. Both sessions must resolve to the same enrolled owner. An anonymous browser must reach Google sign-in before application content. If an already available, non-allowlisted test account is used, it must be denied at IAP without an access grant. Exercise account-mismatch and callback replay locally regardless. Record revision, time, pass/fail per check, denial layer and whether the private binding was stable. Keep raw tokens, cookies, codes, addresses and subject identifiers out of evidence. A mismatched or inconclusive live identity stops the pilot before invitation routes open.

## 2. Prepare the minimum staging deployment for that check

1. Use proposed service `cra2-invitations-staging` in `ajsamslive/us-west1`, a dedicated runtime service account, separate secrets, and a new staging-only image pinned by digest. Build from the invitation lock on Python 3.13. Bind a new staging entry point to `0.0.0.0:$PORT`; keep the existing loopback CLI for local use. The cloud image must omit fixture authentication, fixture key generation and mailbox CLI access. Its first revision exposes only the identity flow and a content-free health check.
2. Enable direct Cloud Run IAP from the first revision and require the Run invoker IAM check. Grant the IAP service agent service-level `roles/run.invoker`; grant only the confirmed owner service-level `roles/iap.httpsResourceAccessor`. Inspect effective inherited access, conditions and public/group grants before routing traffic. Verify the chosen external/testing OAuth configuration supports the owner. Scope all changes to staging; a required project-wide OAuth, organization-policy or shared network change is a separate decision. [Configure IAP for Cloud Run](https://docs.cloud.google.com/run/docs/securing/identity-aware-proxy-cloud-run)
3. Verify staging-only egress for the OIDC discovery/key and token endpoints and IAP public keys. The [existing deployment record](../../docs/cloud-run-plan.md) describes a narrower production egress policy. Store the app OAuth secret in Secret Manager with access restricted to that secret. Validate secure, host-only cookies through the actual cross-site HTTPS callback and CSRF/origin checks on application writes. Check platform request logs as well as application logs for callback query parameters using a synthetic marker before accepting real credentials.
4. Keep minimum instances at zero and initially cap maximum instances at one. Confirm staging spend and teardown time before provisioning. Use a staging-only transactional store for expiring sign-in state and sessions across instance replacement. Test a restart between login start and callback for safe completion or a clean restart with no authenticated session. The container filesystem and the local SQLite directory are unsuitable as durable Cloud Run state. [Cloud Run container contract](https://docs.cloud.google.com/run/docs/container-contract#filesystem)

## 3. Rehearse the invitation flow after the identity check passes

- Add an owner-only rehearsal view. The owner remains the single authenticated human. Distinct synthetic applicants and recipients are records in an isolated test scenario. All role simulation stays inside that scenario and confers no Google or CRA2 workspace access.
- Persist staging invitation state, original synthetic mail receipts, and one-use redemptions transactionally. Use an owner-only synthetic mailbox and reporting copy. Drive dispatch/provisioning with a bounded, idempotent rehearsal operation so progress survives request-based CPU suspension or scale-to-zero. Keep real mail, Google Sheets writes, IAM grant workers, and independent labeling disabled. The runtime needs no mail-sending privilege, production storage access or IAM policy-writing role.
- Rehearse request → owner approval → explicit synthetic send → matching synthetic redemption. Prove approval alone gives zero deliveries, a duplicate send produces one receipt, the code expires exactly 600 seconds after that receipt, revocation denies the synthetic workspace on its next request, and restart preserves each outcome. Record synthetic delivery count separately from real sends and external grants, both of which must be zero.

## Evidence, rollback and review decision

Retain a redacted record of the source SHA, image digest, service revision, effective staging access inventory, Python 3.13 CI results, browser checks, restart results and real-send/grant counts. Compare production revision, traffic and access bindings before and after the exercise. Exclude the permanently locked production audit bucket from staging. Apply a short, agreed TTL to staging session and rehearsal data.

On an unexpected admission, binding mismatch, sensitive log entry, or real delivery/grant attempt, disable the staging rehearsal and restrict staging access immediately. Return traffic to the known identity-only staging revision if available, invalidate staging sessions/codes, and verify denial with a fresh browser. On completion, remove staging-only access and resources against the recorded inventory after preserving redacted evidence.

**Approved local scope.** The implementation slice is the staging identity adapter and its Python 3.13 contract tests. Creating the staging service or OAuth client, granting staging IAM, and conducting the live owner sign-in are subsequent actions. Production stays owner-only. Real invitations and independent labeling stay on hold.
